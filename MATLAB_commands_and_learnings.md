## 1. Setting Up the MATLAB Working Directory

Before running any MATLAB script, it is important to ensure that MATLAB is accessing the correct project folder. MATLAB can execute a file if it is present in the current working directory or in a directory included in the MATLAB search path.

I used the following commands to set up the working directory and verify that all the required files and toolboxes were available.

```matlab
cd 'C:\Users\PRANAYA SINGLA\OneDrive\Desktop\IEEE'
pwd
which guardian_params
ver control
```

The purpose of each command is explained below:

- `cd 'path'`: Changes the current working directory to the specified folder. Since my folder name contained spaces, I enclosed the path in quotation marks.
- `pwd`: Displays the current working directory so that I can verify whether MATLAB is accessing the correct folder.
- `which guardian_params`: Checks whether MATLAB can locate the file `guardian_params.m` and displays its location.
- `ver control`: Checks whether the Control System Toolbox is installed and displays its version.

Initially, when I tried running `design_analysis`, MATLAB displayed the error "Unrecognized function or variable 'guardian_params'". This happened because MATLAB was not accessing the project directory. Changing the working directory resolved this issue.

One additional point I learned was that MATLAB commands and Windows Command Prompt commands are not always interchangeable. For example, `cd` can be used in both environments, but the syntax differs. In Windows Command Prompt, I needed to use double quotation marks and the `/d` option to change drives as well as directories.

## 3. How I Obtained the Results Used in the Paper

### 3.1 Extracting the Results and Monte Carlo Summary

The main results were obtained by running `run_all.m`.

At the beginning of this script, the command `diary('results.txt')` is used. The `diary` command records the output displayed in the MATLAB Command Window and saves it in a text file called `results.txt`.

After running the script, I referred to this file and extracted the required values for the paper. These values were then entered into the corresponding `\newcommand` definitions at the beginning of `main.tex`.

For example:

```latex
\newcommand{\tIntC}{2.37}
```

This approach made it easier to update the results throughout the paper. Instead of manually changing the same number at multiple locations, I only needed to update its definition once.

### 3.2 Investigating the Missed Pulse and Late Interception

While analysing the Monte Carlo results, I wanted to identify the reason behind the single missed pulse. For this, I wrote a small loop that simulated all 200 random cases and printed the pulses with a miss distance greater than 2 m.

The MATLAB code used was:

```matlab
for m = 1:200
    o = simulate_engagement(1000+m);
    i = find(o.pulses(:,2) > 2, 1);
    if ~isempty(i)
        fprintf('case %d: miss %.2f m at t = %.2f s\n', ...
            m, o.pulses(i,2), o.pulses(i,1));
    end
end
```

The output identified the following case:

`case 17: miss 2.81 m at t = 2.44 s`

There were 1615 pulses in total across the simulations, of which 1614 were successful.

I then investigated this particular case in more detail. The first successful hit occurred at 1.119 s, with a miss distance of 0.43 m. The missed pulse was the second pulse, released at 2.4450 s, with a miss distance of 2.8079 m.

I also checked the radar measurements around this time. All 10 radar samples in the preceding 0.5 seconds were valid, which indicated that the missed pulse was not caused by a radar data loss. The actual target acceleration during this period was between 17 and 19 m/s².

To identify the case with the latest interception time, I ran another loop. This gave:

`late case 58: t_int 2.385`

This additional investigation helped me understand that the missed pulse was associated with the target's motion and acceleration rather than a loss of radar measurements.

### 3.3 Studying the Effect of the Simulation Time Step

I also wanted to check how sensitive the simulation results were to the selected time step. The original simulation used a time step of 1 ms.

To compare the results, I tested three different time steps: 1 ms, 10 ms and 50 ms.

The code used was:

```matlab
for dt = [1e-3 1e-2 5e-2]
    for sc = {'A','B','C'}
        o = simulate_engagement(sc{1}, dt);
        fprintf('dt=%g %s: t_int %.3f, pulses %d, hits %d\n', ...
            dt, sc{1}, o.t_intercept, o.n_pulses, o.n_hits);
    end
end
```

The results showed that the interception times at 1 ms and 10 ms were almost identical. The first-hit times were approximately 1.1 s for Scenarios A and B and 2.4 s for Scenario C.

However, when I increased the time step to 50 ms, the results changed considerably. Although every released pulse still resulted in a hit, the first interception time shifted to approximately 2.3 to 2.4 s. The number of pulses also decreased from 9, 9 and 8 to 5, 2 and 4 for Scenarios A, B and C, respectively.

This helped me understand why the simulation time step is an important parameter. A larger time step can affect the timing of events and the number of pulses generated, even if the simulation continues to produce successful hits.

## 4. Understanding the Different Code Files

During the project, I also went through the individual MATLAB files to understand the purpose of each one and how they interacted with one another.

The main files and their functions are summarised below.

- `guardian_params.m`: Contains the physical parameters, controller settings and other derived values used throughout the project. Keeping these values in one file makes it easier to modify the design without changing multiple scripts.

- `turret_plant.m`: Defines the plant equations in the form of differential equations. These equations describe the behaviour of the turret system.

- `turret_controller.m`: Implements the controller, including the Kalman filter, target prediction, compensator and firing conditions.

- `target_motion_generator.m`: Generates the target trajectory, noisy radar measurements, predefined scenarios A, B and C, and random test cases.

- `simulate_engagement.m`: Simulates one complete 10-second engagement using the fourth-order Runge-Kutta method with a time step of 1 ms. It also records the number of pulses and calculates the miss distances.

- `run_all.m`: Runs all the predefined scenarios and Monte Carlo simulations.

- `save_fig.m`: Saves the generated MATLAB figures as PDF files.

- `design_analysis.m`: Performs the control system analysis, including transfer function calculations, pole analysis, stability margins and step response.

- `robust_check.m`: Checks the stability of the system when the plant parameters are varied.

- `study.m` and `tune_study.m`: Used for studying the effect of different design parameters on system performance.

- `make_frames.m`: Generates snapshots of the engagement process.

- `make_estimation_fig.m`: Generates figures related to the estimation error and uncertainty.

- `animate_video.m` and `animate_engagement.m`: Generate animations of the simulated engagement.

- `self_check.m`: Independently verifies the important calculations and results obtained from the main scripts.

A more detailed explanation of the individual files is available in `MATLAB_code_guide.md`.

## 5. MATLAB Concepts and Learnings

Working on this project gave me an opportunity to learn several MATLAB concepts while implementing and testing an actual engineering system.

### 5.1 Basic MATLAB Concepts

The following are some of the important concepts I learned during the process:

- **Functions and scripts:** A MATLAB function file begins with the `function` keyword, and its name should match the file name. A script does not require this declaration and cannot be called with input arguments in the same way as a function. I initially encountered an error when I tried to execute a script as a function.

- **Persistent variables:** The `persistent` keyword allows a variable to retain its value between successive function calls. In this project, it was used to maintain the internal state of the Kalman filter in the controller.

- **Random number generation:** The `rng(seed)` command sets the random number generator to a particular starting state. This makes random simulations repeatable. For example, using the same seed ensures that case 17 produces the same target motion and simulation results every time.

- **Matrix exponential:** The `expm` command calculates the matrix exponential. I learned how it can be used for the exact discretisation of the compensator. I also compared the result with MATLAB's `c2d` command to check whether both approaches gave consistent results.

- **Recording output:** The `diary` command records the output displayed in the Command Window and saves it to a text file. This was particularly useful for extracting the results of multiple simulations.

- **Global variables:** The `global` keyword allows variables to be accessed by different functions without passing them as input arguments. The `tune_study` script uses this approach. I also learned that global variables need to be handled carefully, especially when a script is interrupted midway.

- **Clearing functions:** The `clear functions` command clears loaded functions and resets their persistent variables. This was useful when I needed to restart the controller or reload modified code.

### 5.2 Errors Encountered and How I Resolved Them

During the implementation, I encountered several errors. Understanding their causes was an important part of learning how MATLAB works.

- **MATLAB could not find a function:** This happened because the current working directory was not set correctly. I resolved it by using `cd` to move to the project folder.

- **Control System Toolbox was missing:** The `tf` command generated an error because the required toolbox was not installed. Installing the Control System Toolbox resolved the issue.

- **Using MATLAB commands in Windows Command Prompt:** I initially confused the two environments. I learned that commands such as `which`, `pwd` and `ver` must be executed inside MATLAB.

- **Character vector is not terminated properly:** This error occurred when I pasted a long `sprintf` statement and the text was split incorrectly. I fixed it by keeping the strings on a single line and checking that all quotation marks were properly closed.

- **Variable not found:** The variable `np_` was unavailable because the `run_all` script cleared the workspace before execution. I resolved this by running the required calculations again instead of depending on a variable that had already been deleted.

- **Misinterpreting radar availability:** Initially, I incorrectly interpreted the `meas_valid` output as an indication of radar data loss. However, I later understood that this variable is equal to 1 only at the 20 Hz radar sampling instants. Between these instants, it is 0 even when there is no radar loss. I therefore discarded my initial interpretation.

- **Controller settings remaining active after stopping a simulation:** When I interrupted `tune_study` using Ctrl+C, the parameter override remained active. I resolved this by resetting `GUARDIAN_OVERRIDE` to an empty value, clearing the loaded functions and checking that the original values of `P.q` and `P.K` had been restored.

These errors helped me become more comfortable with debugging, checking variables and understanding how different MATLAB files interact.

### 5.3 Engineering Learnings

Apart from learning MATLAB, the project also helped me understand some important aspects of engineering implementation and result verification.

1. **Maintaining a single source of parameters:** Keeping all the physical and controller parameters in `guardian_params.m` made the code easier to manage. It also reduced the possibility of using different values in different parts of the project or in the final paper.

2. **Independent verification of results:** I learned that it is important not to rely only on the output of the main simulation. The `self_check.m` script recalculates important quantities, including the plant, poles, stability margins, delay matching and discretisation, through a separate approach. All 12 checks passed.

3. **Using actual simulation results:** During the initial stages, I had also worked with a Python implementation of the model. However, some results differed from the MATLAB implementation, particularly regarding Scenario B availability, maximum miss distance and Monte Carlo hit ratio. I therefore used the results obtained directly from my final MATLAB implementation in the paper.

4. **Verifying claims before including them:** I realised that every numerical claim in the paper should be supported by an actual calculation or simulation. Wherever the results did not support an initial assumption, I corrected the statement or removed it.

5. **Reporting limitations clearly:** It is equally important to discuss the limitations of the system. For example, the Monte Carlo simulation included one missed pulse, increasing the simulation time step to 50 ms affected the interception time, and the system has not yet undergone instructor evaluation. These points should be reported honestly rather than presenting only the successful results.
